Appendix B

Git, Visualised

Appendix A explains git in prose. This one shows it moving. Step through the exact workflow you used for Chapter 3 — branch, commit, push, review, merge, pull — and watch the labels slide, diverge, and come back together.

The one idea everything else rests on

A branch is not a folder and not a copy of your code. It is a 41-byte file containing a commit id — a sticky note stuck on one commit in a chain. When you make a new commit, the note peels off and moves forward onto it.

Every confusing thing about git becomes simple once you can see which sticky note is where. The trouble is that there are three separate sets of them, they drift apart during ordinary work, and only one set is actually yours.

The three sets of labels

Your machine. main, ch03-submissions — the branches you can move by committing. HEAD marks which one you are standing on.

Your memory of GitHub. origin/main, origin/ch03-submissions — not GitHub's labels. A cached note of where they were the last time you asked. Memories go stale, and nothing tells you when.

GitHub. Its own main, which it moves without consulting you — when you click Merge, for instance.

What the replay showed

Committing moves exactly one label. The branch you are standing on slides forward; every other label stays exactly where it was. That is why main was untouched for the whole of Chapter 3 — you were never standing on it.

Pushing does not move your labels. It copies commits to GitHub and updates GitHub's label, then refreshes your memory of it. Nothing on your machine changes position.

A pull request moves nothing at all. It is a request to compare two labels and, eventually, to move one of them. This is why the branch must exist first: with no branch there is no difference, so there is nothing to review, nothing for CI to run against, and nowhere for review comments to attach.

Merging on the website moves GitHub's label and nothing of yours. This is the moment the three sets diverge, and the one that catches everybody — including you, between Chapters 1 and 2, when ch02-submissions was cut from a stale main and was born missing your own Chapter 1 work.

fetch updates your memory. pull updates your memory and your files. That is the whole difference between them.

Why git switch main comes first pull updates the branch you are standing on. Standing on ch03-submissions and pulling would drag the merge commit onto that branch instead of onto main — leaving main still stale and your next branch still born wrong. The switch is not politeness; it chooses the target.
