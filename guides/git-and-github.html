Appendix A

Git, GitHub, and the Working Loop

Every professional codebase you will ever touch is under version control, and almost every team ships through pull requests with automated checks. This appendix explains what those things actually are — not which buttons to press, but what is happening underneath, so the daily commands stop being incantations.

Part 1 · Git, on your own machine

The problem version control solves

Without version control, a codebase has exactly one state: whatever is on disk right now. Change a file and the previous version is gone. Two people editing the same project overwrite each other. There is no way to ask "what did this look like last Tuesday", or "who changed this line and why", or "undo the last three hours but keep the hour before".

Git solves this by recording snapshots of your entire project over time, along with who made each one and why. Everything else — branches, merges, pull requests — is built on that single idea.

Git is not GitHub Git is a program on your computer. It works completely offline and has nothing to do with any website. GitHub is a company that hosts Git repositories and adds collaboration features on top — pull requests, code review, automation. You could use Git forever without GitHub. Keeping the two separate in your head prevents a lot of confusion later.

The three areas

This is the piece most people never get told explicitly, and it makes git add feel arbitrary until you know it. Git has three places a change can live.

The staging area exists so that a commit can be deliberate. You might have edited four files but only two of them belong to the change you want to record. git add is you saying "these, not those". Without it, every commit would be "everything currently different", which makes history far less useful to read later.

What a commit actually is

Definition

A commit is a permanent, immutable record containing: a complete snapshot of every tracked file at that moment, a pointer to the commit that came before it (its parent), the author and timestamp, a message explaining why, and a unique 40-character identifier — its SHA — computed from all of the above.

Two consequences follow from that definition, and both matter daily.

Commits form a chain. Because each commit points at its parent, history is a linked sequence running backwards from the newest commit to the very first. That chain is the history — there is no separate log file.

Commits are immutable. You cannot edit a commit. Commands that appear to (--amend, rebase) actually build new commits and move pointers to them; the originals are simply abandoned. This is why rewriting history that other people have already pulled is antisocial — their chain no longer matches yours.

Branches are pointers, not copies

This is the single most useful thing to understand about Git, and almost everyone starts out believing something else. People assume a branch is a copy of the project. It is not.

Definition

A branch is a movable pointer to one commit. That is the entire implementation. Creating a branch writes a file containing a 40-character SHA — it does not copy a single line of your code.

Because a branch is just a label, branching is instant and free regardless of project size, and deleting a branch destroys nothing that has been merged — it removes a label, not commits.

HEAD is a further pointer, and it points at whichever branch you are currently on. That is what "which branch am I on" means mechanically. git switch main moves HEAD to main and updates the files on disk to match that commit.

Watch the pointers move

Merging

Merging combines the work of two branches. Git has more than one way to do it, and the difference shows up in what your history looks like afterwards.

KindWhat happensWhen you see it
Fast-forwardmain has not moved since you branched, so Git simply slides main's pointer forward to your latest commit. No new commit is made.Simple, linear work
Merge commitBoth branches moved. Git creates a new commit with two parents, joining the histories.Parallel work by several people
Squash mergeAll the commits on your branch are combined into a single new commit on main. Your branch's individual commits are not copied over.What this repository uses

Squashing gives you the best of both: granular commits while you work (useful for you, and for anyone reviewing your process), and one clean entry per chapter on main (useful for anyone reading the project's history later). The detailed history still exists on the pull request permanently.

Remotes

A remote is another copy of the repository, usually on a server. Yours is called origin — a convention, not a keyword — and lives on GitHub.

CommandWhat it does
git fetchDownloads new commits from the remote. Changes nothing you are working on.
git pullfetch, then merge those commits into your current branch. Changes your files.
git pushUploads your commits to the remote.

Your local main and the remote's main are separate pointers that can disagree. Git tracks the remote's position as origin/main, which is why git status can tell you that you are "3 commits ahead" — it is comparing two labels.

Part 2 · GitHub, on top of Git

GitHub hosts your repository and adds a collaboration layer. Everything in this part is a GitHub feature — none of it exists in Git itself.

What a pull request actually is

A pull request is the piece people find most mysterious, usually because the name is a historical accident. It is worth being precise.

Definition

A pull request is a request to merge one branch into another, plus everything that gathers around that request: the accumulated diff, a discussion thread, line-by-line review comments, and the results of any automated checks. It is a proposal, held open until someone decides.

The name comes from the era of mailing lists: you would email a maintainer asking them to pull your changes into their copy. GitHub kept the phrase and built an interface around it. Nothing is being pulled by you — you are asking for your branch to be merged.

Four things a pull request gives you that a bare merge does not:

  • A reviewable unit. The diff between your branch and the target, as one coherent change rather than a scattering of commits.
  • A place for judgment. Comments attached to specific lines, which is where code review actually happens.
  • A trigger for automation. Opening or updating a pull request is an event other systems can react to — which is how tests come to run on it.
  • A permanent record. Long after the branch is deleted, the pull request preserves what changed, what was said about it, and what the tests reported.

The behaviour that surprises everyone once: a pull request tracks a branch, not a snapshot. Push another commit to that branch and the pull request updates itself and re-runs its checks. You never open a second pull request to fix something in the first.

Review

A reviewer reads the diff and leaves comments on specific lines, then concludes with one of three outcomes: approve, request changes (a block, until addressed), or comment (observations, no verdict). You respond by pushing more commits to the same branch.

A wrinkle in this repository GitHub does not let you formally approve your own pull request. Here, review arrives as comments and change requests rather than a green "approved" badge, and the automated check is the real gate. The substance is identical; only the badge is missing.

Part 3 · Continuous integration

What the phrase actually means

"Continuous integration" is older than GitHub and describes a practice, not a product. To understand it, consider the alternative that it was invented to kill.

Teams used to work in isolation for weeks, then combine everything at the end. That final combination was reliably catastrophic — a hundred small incompatibilities surfacing simultaneously, each one now buried under weeks of subsequent work. The industry called it integration hell, and it could consume as much time as the original development.

Definition

Continuous integration is the practice of merging work into a shared mainline frequently — daily or more — with automated verification on every merge, so that incompatibilities surface within minutes of being created, while the change is still small and still fresh in the author's mind.

The word "continuous" refers to the frequency of integration, not to a machine running constantly. The automation is what makes frequent integration practical, which is why "CI" has come to mean the automation in everyday speech.

What it is mechanically

When you push, GitHub reads .github/workflows/grade.yml and, if the event matches, allocates a fresh virtual machine — a runner — that has never seen your project. It then executes your steps in order: check out the code, install Python, install pytest, run the suite. The exit status of those steps determines whether the check passes.

Why a clean machine matters so much. Your laptop has years of accumulated state — installed packages, environment variables, files you forgot you created. Code can depend on that state without anyone realising, which produces the oldest excuse in software: "it works on my machine." A runner that starts empty every time cannot be fooled. If it passes there, it will pass for anyone.

Red and green

Green means every step exited successfully — here, that every test passed. Red means something exited non-zero. Red is information, not judgment: it is a machine reporting that a specific assertion did not hold, and the log names which one and what it expected. It is the cheapest, fastest, least personal feedback in the entire process, which is exactly why you want it to run before a human looks at anything.

What green does not mean Green means the code meets the published specification. It does not mean the code is good. A solution can pass every visible test and still be wrong in ways the tests do not reach, or correct but badly expressed. That is what review is for, and it is why passing checks is the floor rather than the finish line.

Part 4 · The commands, and what each one really does

CommandWhat is actually happening
git statusReports all three areas at once: what has changed on disk, what is staged, and how your branch compares with origin. Run it constantly.
git switch mainPoints HEAD at main and rewrites the files on disk to match that commit.
git switch -c ch01-submissionsCreates a new label pointing at the current commit, then points HEAD at it. No files change — the new branch starts identical.
git pullDownloads new commits from origin and merges them into your current branch.
git add <file>Copies that file's current state into the staging area — your declaration of what belongs in the next commit.
git commit -m "…"Records everything staged as a new immutable commit, with your message, pointing at the current commit as its parent. Moves the branch label forward.
git diffShows changes on disk that are not staged. Add --staged to see what is.
git log --onelineWalks the parent chain backwards from where you are, one line per commit.
git push -u origin ch01-submissionsUploads the branch and records that it corresponds to origin's copy. The -u is needed only the first time; afterwards git push alone is enough.
gh pr create --fillOpens a pull request proposing your branch be merged into main, using your commit messages for the title and body.
gh pr checks --watchPolls the automated checks and prints their status as they complete.
gh pr merge --squash --delete-branchCombines your branch's commits into one commit on main, then deletes the branch locally and remotely.

Part 5 · Why the platform works this way

None of the above is a teaching device invented for this syllabus. It is, almost exactly, how professional software teams operate, and the overlap is deliberate.

Feature branches are the industry default. The overwhelming majority of teams work on short-lived branches cut from a protected mainline. The pattern is old, stable, and near-universal.

Almost nothing reaches production without a pull request. Whatever the company, whatever the language, the unit of work is a branch proposed for merge, discussed, and approved. Arriving at a job already fluent in that loop removes a real source of early friction — most people learn it on the job, awkwardly, in their first weeks.

Code review is the most consistent practice in good engineering organisations. Being reviewed is a skill: reading criticism of your work as information rather than verdict, responding with a commit rather than an argument, knowing when to push back. It only develops by being reviewed repeatedly, which is why review is built into this platform rather than bolted on.

Automated checks gate merges everywhere. Red-means-stop is the ambient condition of professional work.

There is also a narrower reason, specific to learning. The exercises here must be attempted unaided — and unaided work needs feedback that is immediate, objective, and impersonal, or the temptation to look something up becomes overwhelming. A machine that says "line 3 printed £11.72 where £11.73 was expected" gives you exactly enough to find your own error and nothing that solves it for you. That is a better teacher than a hint, and a far better one than an answer.

Finally: the record. A repository with dozens of merged pull requests, each carrying a real test run and a real review conversation, is evidence of sustained practice that a finished project cannot show. The project shows what you can build. The history shows how you work.
