Chapter Four

Keeping What You Find

Every program you have written so far could count things without being able to keep them. Chapter 3's duplicate scan found four pairs and could not tell you which four. This chapter is about the sequence that grows — and a returns desk that has no idea how many items it will take back until the day is over.

Why this chapter exists

Chapter 3 gave you iteration, and with it the ability to do one thing to every item in a batch. But look carefully at what all six exercises had in common: they could count, and they could print, and they could total — and not one of them could keep anything.

Exercise 3 is the sharpest case. It scanned a supplier feed and found four duplicate pairs, printing each one as it went. Now ask that program a question it ought to be able to answer: which pairs did you find?

It cannot tell you. After the loop, pairs holds the number 4, and every position it discovered has been printed to the screen and forgotten. The information existed for one instant inside the loop body and was never stored anywhere, because there was nowhere to store it.

The exact limitation A tuple is fixed the moment it is created. Its length is decided at birth and can never change. So a tuple cannot be the answer to "collect everything the scan finds", because you do not know how many that is until the scan has finished — and by then it is too late to have made a tuple of the right size.

This is not an unusual situation. It is the ordinary one. A returns desk does not know how many items will come back today. A log scan does not know how many errors it will find. A validation pass does not know how many rows will fail. In every case the size of the answer is discovered by doing the work, not known before it starts.

The tool for that is the list, and this chapter is about earning it — building the behaviour by hand before reaching for the built-in version, exactly as Chapter 3 built the accumulator before meeting sum.

The running example is a returns desk at a warehouse. Items come back from customers; each is inspected and either goes back into sellable stock or is written off. Nobody knows the split until the day is done.

1. The list: a sequence that can change

A list is written with square brackets instead of parentheses:

restock = ["SKU-101", "SKU-104", "SKU-109"]
print(restock)
print(type(restock))
print(len(restock))
print(restock[0])
print(restock[-1])
['SKU-101', 'SKU-104', 'SKU-109'] <class 'list'> 3 SKU-101 SKU-109

Line by line. ["SKU-101", "SKU-104", "SKU-109"] is a list literal — square brackets, items separated by commas. print(restock) shows the whole list, and note that Python echoes it back in the same bracket notation, with single quotes around the strings. type(restock) reports <class 'list'>, a different type from tuple. len counts items exactly as it did for tuples and strings. restock[0] indexes from zero, and restock[-1] counts back from the end.

Everything in that list is something you already know how to do, because a list supports every read operation a tuple supports — indexing, negative indexing, len, iteration with for, membership with in, and IndexError when you ask for a position that does not exist.

for sku in restock:
    print(f"restocking {sku}")

print("SKU-104" in restock)
print("SKU-999" in restock)
restocking SKU-101 restocking SKU-104 restocking SKU-109 True False

So if lists can do everything tuples can do, why does the language have both? Because of one difference, and it is the entire point of the chapter.

Definition

A list is a sequence of values in order, like a tuple, except that it is mutable — its contents and its length can be changed after it has been created. Its type is list, and it is written with square brackets: [1, 2, 3]. The empty list is [].

Mutable means changeable in place. A tuple is immutable: once made, that is what it is forever. The word is worth learning because it divides Python's types into two camps and explains a great deal of behaviour later on.

One piece of punctuation to notice: the empty list is simply [], with no comma trick required. Compare that with the one-item tuple ("GB",) from Chapter 3, which needed a trailing comma to distinguish it from parentheses used for grouping. Square brackets have no other job, so there is no ambiguity to resolve.

2. Growing a list: append

Here is the move the whole chapter is built on. Start with an empty list and add to it as you discover things:

restock = []
print(restock)
print(len(restock))

restock.append("SKU-101")
print(restock)

restock.append("SKU-104")
print(restock)
print(len(restock))
[] 0 ['SKU-101'] ['SKU-101', 'SKU-104'] 2

restock.append("SKU-101") deserves a full unpacking, because the syntax is new.

The dot is attribute access: it means "the thing named append that belongs to the object restock". append is a method — a function that belongs to a particular object and acts on it. You have used functions before (print, len, float) and they stand alone; a method is written after the object it works on, joined by a dot. len(restock) is a function call taking the list as an argument; restock.append(x) is a method call on the list itself.

What append does: it adds one item to the end of the list, increasing its length by one. It does this in place — the list named restock is modified. There is no new list.

The trap that catches everyone once append returns None, not the list. So restock = restock.append("SKU-101") does not grow the list and assign it back — it appends, then replaces your list with None, and everything afterwards fails with AttributeError: 'NoneType' object has no attribute 'append'. Call it as a statement on its own line, never as something to assign. This is true of every method in Python that changes an object in place, and it is deliberate: the language uses the None return to tell you "I mutated the thing you gave me; I did not make you a new one."

Now the pattern that matters. Chapter 3 taught the accumulator: initialise before the loop, update inside, use after. This is the same pattern with a list instead of a number — and where a numeric accumulator collapses everything into one value, a list accumulator keeps every value.

returns = (
    ("SKU-101", "SEALED"),
    ("SKU-102", "DAMAGED"),
    ("SKU-104", "SEALED"),
    ("SKU-107", "DAMAGED"),
    ("SKU-109", "SEALED"),
)

restock = []
writeoff = []

for sku, condition in returns:
    if condition == "SEALED":
        restock.append(sku)
    else:
        writeoff.append(sku)

print(f"restock  {len(restock)}: {restock}")
print(f"writeoff {len(writeoff)}: {writeoff}")
restock 3: ['SKU-101', 'SKU-104', 'SKU-109'] writeoff 2: ['SKU-102', 'SKU-107']

Two lists, both empty before the loop, both grown inside it, both used after. Neither length was known in advance — they were discovered by doing the work. That is the thing a tuple could not do.

Notice also that the input returns is still a tuple of tuples, exactly as in Chapter 3. The incoming data has a fixed shape and should not change, so a tuple is right for it. The results are collections that grow, so lists are right for them. Section 4 makes that choice explicit.

3. Changing an item in place

The second thing mutability buys you is the ability to replace an item that is already there:

counts = [0, 0, 0]
print(counts)

counts[1] = 7
print(counts)

counts[1] = counts[1] + 1
print(counts)
[0, 0, 0] [0, 7, 0] [0, 8, 0]

counts[1] = 7 reads left-to-right as "the item at position 1 of counts becomes 7". You have seen counts[1] before, on the right-hand side, as a way of reading a position. On the left-hand side of = it writes that position instead. The list keeps its length; one slot now holds something different.

counts[1] = counts[1] + 1 does both in one line: read position 1, add one, write the result back to position 1. This is the accumulator pattern again, except the running total lives in a slot of a list rather than in a name of its own — which means you can keep several running totals at once without inventing several names.

Try the same thing on a tuple and Python refuses outright:

sizes = (10, 20, 30)
sizes[1] = 99
Traceback (most recent call last): File "example.py", line 2, in <module> sizes[1] = 99 ~~~~~~~~^^^^^ TypeError: 'tuple' object does not support item assignment

Read the error precisely: does not support item assignment. It is not that the value 99 is wrong, or that position 1 does not exist. The operation itself is unavailable on this type. That is immutability enforced by the language rather than by convention.

A model for the difference Picture a tuple as a row printed on paper — you can read any part of it, and to change anything you must print a new row. A list is a row of pigeonholes: the shelf stays put, and you can swap what is in any hole, or bolt another hole onto the end. Both let you read slot 3. Only one lets you change what is in it.

4. Which to reach for: list or tuple

Both hold several values in order. Both index from zero. Both work with for, len and in. So the choice is not about capability, and reaching for a list every time "because it can do more" is the wrong instinct.

tuplelist

Empty()[]
One item(a,) — comma required[a]
Can grow or shrinknoyes

Natural meaningone record: fields of different kinds, in a fixed orderone collection: many things of the same kind, however many there turn out to be
Typical usea row: ("SKU-101", 12, True)the results you gather: ["SKU-101", "SKU-104"]

The distinction worth internalising is record versus collection, and it is about meaning rather than mechanics.

A tuple usually holds a fixed number of fields that mean different things — (sku, quantity, active) is a product line, and position 0 is always the code while position 2 is always the flag. Its length is part of its shape, which is why unpacking with for sku, quantity, active in rows: works and reads well.

A list usually holds any number of things that all mean the same thing — every SKU to restock, every order that failed validation. Its length is data, not shape. It would be meaningless to unpack it into named variables, because you do not know how many there are.

This is exactly the arrangement in the returns example: the incoming data is a tuple of tuples, because each row is a record and the batch is fixed once it arrives. The outputs are lists, because they are collections whose sizes are discovered.

There is a second, quieter reason to prefer a tuple where one fits: a value that cannot change cannot be changed by accident. If a piece of data is not supposed to be modified, a tuple makes modifying it an error rather than a bug. That protection is free, and it is why ALLOWED = ("GB", "IE", "FR") in the previous chapters was correctly a tuple and not a list.

5. Removing and inserting, and what each costs

Three more methods complete the everyday set. Each changes the list in place.

queue = ["ORD-1", "ORD-2", "ORD-3", "ORD-4"]

last = queue.pop()
print(last, queue)

first = queue.pop(0)
print(first, queue)

queue.insert(0, "ORD-URGENT")
print(queue)

queue.remove("ORD-3")
print(queue)
ORD-4 ['ORD-1', 'ORD-2', 'ORD-3'] ORD-1 ['ORD-2', 'ORD-3'] ['ORD-URGENT', 'ORD-2', 'ORD-3'] ['ORD-URGENT', 'ORD-2']

pop() with no argument removes the last item and — unlike append — returns it, which is why last = queue.pop() is correct and useful. pop(0) removes the item at a given position instead, again returning it. insert(0, x) puts x at position 0 and shifts everything after it one place right. remove(x) deletes the first item equal to x, searching by value rather than by position.

Two failure modes to know before you meet them at speed:

empty = []
empty.pop()
IndexError: pop from empty list
letters = ["a", "b"]
letters.remove("z")
ValueError: list.remove(x): x not in list

pop on an empty list raises IndexError; remove for a value that is not present raises ValueError. Both are the "the loop found nothing" case wearing a different hat — the same class of problem as a summary line that assumes it has something to summarise. Guard with if lst: or if x in lst: before calling either.

A note on cost, which will matter later These operations are not equally cheap. append() and pop() at the end are effectively instant regardless of how long the list is. insert(0, x), pop(0) and remove(x) are not: every item after the affected position has to shift along by one, so the work grows with the length of the list. On ten items nobody notices. On a hundred thousand, a loop that repeatedly does pop(0) is quietly doing billions of moves. There is a structure built for cheap removal from the front — collections.deque — and it arrives in the queues chapter, where the problem that needs it does.

An empty list is falsy, exactly as an empty tuple and an empty string are, which makes the guard read naturally:

found = []

if found:
    print(f"{len(found)} matches")
else:
    print("no matches")
no matches

if found: is idiomatic Python for "if this list has anything in it". Writing if len(found) > 0: is not wrong, and it is clearer to a beginner, but the shorter form is what you will read in real code and it says the same thing.

6. Build before you borrow: the accumulators you have already written

Across Chapters 1 to 3 you wrote running totals, running counts and running maxima by hand, six exercises' worth. That was deliberate. Now that the pattern is in your fingers, here is what it looks like over a list — and then the built-in that replaces it.

The hand-written versions, using nothing this syllabus has not taught:

values = [45, 12, 88, 3, 27]

total = 0
for v in values:
    total = total + v

biggest = None
for v in values:
    if biggest is None or v > biggest:
        biggest = v

print(total, biggest)
175 88

The biggest loop is worth re-reading. It starts at None rather than at zero, because zero would be wrong the moment every value is negative — 0 is not a member of the data and has no business winning. None means "nothing seen yet", and biggest is None or v > biggest reads as "take this value if we have nothing, or if it beats what we have". Python evaluates or left to right and stops as soon as one side is true, so when biggest is None the comparison v > biggest is never attempted — which matters, because comparing a number with None raises TypeError.

Now the borrowed versions:

values = [45, 12, 88, 3, 27]

print(sum(values))
print(max(values))
print(min(values))
print(len(values))
175 88 3 5

sum, max and min are built-in functions — always available, no import needed. Each takes a sequence and returns a single value. They work on lists, tuples and anything else you can loop over. sum requires numbers; max and min work on anything Python can compare, including strings, where they give alphabetical order.

These are not magic and they are not faster because they are clever — they are the loop you just wrote, implemented once in C inside the interpreter. The reason to prefer them is that sum(values) states the intent in one glance, and a four-line loop makes a reader check whether you got it right.

The empty case, which the review has caught you on three times sum([]) is 0, which is sensible. But max([]) and min([]) raise ValueError: max() arg is an empty sequence — because there is no honest answer, and inventing one would be worse than refusing. This is the "what if the loop found nothing" question in built-in form. Any time you call max on something you collected rather than something you were given, ask whether it can be empty, and guard with if values: if it can.

7. Sorting: build it, then borrow it

Ordering a list is the first thing you will want after collecting one — the ten slowest queries, the biggest refunds, the alphabetical picking route. Before meeting the built-in, write one, because a sort you have written is a sort you can reason about.

The algorithm is selection sort, and it is exactly the shape §9 of Chapter 3 taught: an outer loop over every position, an inner loop over every position after it.

values = [45, 12, 88, 3, 27]

for i in range(len(values)):
    smallest = i
    for j in range(i + 1, len(values)):
        if values[j] < values[smallest]:
            smallest = j
    values[i], values[smallest] = values[smallest], values[i]

print(values)
[3, 12, 27, 45, 88]

Walk it. The outer loop stands on position i and its job is to put the correct value there, permanently. smallest = i assumes for now that the value already at i is the smallest of everything remaining — a starting guess, holding a position rather than a value, which is what makes the swap possible later. The inner loop then checks every position after i; whenever it finds something smaller than the current champion, it updates smallest to that position. When the inner loop ends, smallest is the position of the smallest remaining value.

Then the swap: values[i], values[smallest] = values[smallest], values[i]. This is the multiple assignment from Chapter 3, and it works because Python evaluates the entire right-hand side first, building the pair of old values, and only then assigns them to the left. Without that, the first assignment would overwrite a value you still needed. Note that this line requires item assignment — it is impossible on a tuple, which is why sorting belongs in the lists chapter.

After the outer loop's first pass, position 0 holds the smallest value in the list and never changes again. After the second, position 1 is settled. The sorted region grows from the left until nothing is left to place.

The cost is the triangular scan from §9: roughly n × (n − 1) ÷ 2 comparisons. For five values that is ten. For ten thousand it is fifty million, which is why nobody uses selection sort in production — but you now know what a sort is, which is the point.

Step through selection sort

The algorithm from §7, one comparison at a time. i is the position being filled, j is the position being examined, and smallest is the best candidate found so far. Everything left of i is finished and never moves again.

The borrowed version

values = [45, 12, 88, 3, 27]

ordered = sorted(values)
print(ordered)
print(values)

values.sort()
print(values)

print(sorted(values, reverse=True))
[3, 12, 27, 45, 88] [45, 12, 88, 3, 27] [3, 12, 27, 45, 88] [88, 45, 27, 12, 3]

Two different tools, and the difference matters. sorted(values) is a built-in function that returns a new sorted list and leaves the original untouched — look at the second print, which shows values still in its original order. values.sort() is a list method that sorts in place and returns None, exactly like append. Writing ordered = values.sort() is the same trap in a new costume: it sorts the list and hands you None.

reverse=True is a keyword argument — an argument passed by name rather than by position. You will meet these properly in the functions chapter; for now, read it as an option, and note that it works on both sorted and .sort().

Sorting a list of tuples is worth seeing now, because it will do most of the work in this chapter's exercises:

lines = [
    ("SKU-104", 3),
    ("SKU-101", 12),
    ("SKU-109", 7),
]

print(sorted(lines))
[('SKU-101', 12), ('SKU-104', 3), ('SKU-109', 7)]

Tuples are compared field by field: first elements first, and only if those tie does Python look at the second. So sorting a list of (sku, quantity) rows orders them by SKU. To order by quantity instead, build the tuples the other way round — (quantity, sku) — sort, and read the fields back off. That is a real technique, not a workaround, and it is how you sort by any field using only what you now know.

8. enumerate: index and item together

Chapter 3 gave you two ways to loop, and made you feel the gap between them. for sku in feed: gives you the value but not where it sits. for i in range(len(feed)): gives you the position but then makes you write feed[i] every time you want the value.

Often you want both:

picks = ["SKU-101", "SKU-104", "SKU-109"]

for i in range(len(picks)):
    print(f"{i + 1}. {picks[i]}")
1. SKU-101 2. SKU-104 3. SKU-109

That works, and until now it was the only way. But picks[i] is a lookup you are doing by hand on every iteration, and range(len(picks)) is three function calls to say "every position". The built-in that says it directly:

for i, sku in enumerate(picks):
    print(f"{i + 1}. {sku}")
1. SKU-101 2. SKU-104 3. SKU-109

enumerate(picks) hands back a position and an item on every iteration, as a pair — which is why the loop header unpacks two names, exactly as for sku, condition in returns: did with a tuple of tuples. The indexing disappears, and the loop now says what it means.

If your numbering starts at one, say so rather than adding one everywhere:

for n, sku in enumerate(picks, start=1):
    print(f"{n}. {sku}")
1. SKU-101 2. SKU-104 3. SKU-109

start=1 is another keyword argument. The default is 0, which is what you want when the number is a genuine index into the list; start=1 is what you want when it is a line number for a human to read.

When range(len(...)) is still correct enumerate replaces range(len(...)) when you want each item once, in order. It does not replace it when the positions themselves are the subject — the pairwise scan from §9, for j in range(i + 1, len(feed)), cannot be written with enumerate, because the inner loop's bounds depend on the outer position. Both tools stay.

9. zip: two sequences in step

Sometimes related data arrives in two separate sequences that line up by position:

skus = ["SKU-101", "SKU-104", "SKU-109"]
counts = [12, 3, 7]

for sku, count in zip(skus, counts):
    print(f"{sku:<10}{count:>4}")
SKU-101 12 SKU-104 3 SKU-109 7

zip walks both sequences at once, handing back one item from each on every iteration, paired. Without it you would loop over positions and index into both lists by hand, which works and is noisier.

The trap, and it is a quiet one:

skus = ["SKU-101", "SKU-104", "SKU-109"]
counts = [12, 3]

for sku, count in zip(skus, counts):
    print(sku, count)
SKU-101 12 SKU-104 3

zip stops at the shorter sequence and says nothing. SKU-109 was silently dropped. No error, no warning, no clue in the output that anything is missing — you would have to already know there were three SKUs to notice that two came out.

This is the single most dangerous thing in this chapter, because it is data loss that looks like success. If two sequences are supposed to be the same length, check it — if len(skus) != len(counts): — rather than trusting that they are.

10. What this makes possible, and what is still coming

You can now collect results whose size you do not know in advance, change them after the fact, and put them in order. Combined with the previous three chapters, that is enough to write the shape of most small data-processing programs: read a batch, validate it, route it, gather what matters, order it, report it.

Worked examples

Example 1 — The returns desk at close of day

Six items came back. Sealed goods return to sellable stock; damaged goods are written off and their value lost. Produce the two lists and total what the damage cost.

The reasoning before the code. Two outputs are needed and neither size is known in advance, so both are lists built by appending. The restock list only needs the SKU, because nothing else about it matters downstream. The write-off list needs the SKU and the value, because the total has to be computed from it — so each entry is a tuple appended into a list: a record inside a collection, which is the arrangement §4 described.

returns = (
    ("SKU-101", "SEALED",  24.99),
    ("SKU-102", "DAMAGED", 15.50),
    ("SKU-104", "SEALED",  99.00),
    ("SKU-107", "DAMAGED",  8.75),
    ("SKU-109", "SEALED",  24.99),
    ("SKU-112", "DAMAGED", 45.00),
)

restock = []
writeoff = []

for sku, condition, value in returns:
    if condition == "SEALED":
        restock.append(sku)
    else:
        writeoff.append((sku, value))

print(f"RESTOCK ({len(restock)})")
for sku in sorted(restock):
    print(f"  {sku}")

print(f"WRITE-OFF ({len(writeoff)})")
lost = 0.0
for sku, value in writeoff:
    print(f"  {sku:<10}{value:>7.2f}")
    lost = lost + value

print("-" * 24)
if writeoff:
    print(f"lost {lost:,.2f} across {len(writeoff)} items")
else:
    print("nothing written off")
RESTOCK (3) SKU-101 SKU-104 SKU-109 WRITE-OFF (3) SKU-102 15.50 SKU-107 8.75 SKU-112 45.00 ------------------------ lost 69.25 across 3 items

writeoff.append((sku, value)) has two sets of parentheses and both are doing work: the outer pair is the method call, the inner pair builds the tuple. Drop the inner pair and Python reads it as append being given two arguments and refuses, because append adds exactly one item.

for sku, value in writeoff: then unpacks each record on the way back out, exactly as you unpacked rows of a tuple-of-tuples in Chapter 3. The list is a collection of records; looping over it hands you one record at a time.

Finally, if writeoff: guards the summary. On this data it is never false — and that is precisely why it is there. A day where nothing is damaged is a perfectly ordinary day, and lost 0.00 across 0 items is a worse thing to print than a sentence that says so.

Example 2 — The three largest write-offs

Now order the damage. The obstacle: sorted compares tuples field by field starting at the front, so sorting (sku, value) records gives alphabetical order by SKU — not what is wanted.

The technique is to build new tuples with the field you want to sort by in front, sort those, and read the fields back off afterwards.

writeoff = [
    ("SKU-102", 15.50),
    ("SKU-107",  8.75),
    ("SKU-112", 45.00),
    ("SKU-118", 30.00),
    ("SKU-120",  2.99),
]

by_value = []
for sku, value in writeoff:
    by_value.append((value, sku))

by_value.sort(reverse=True)

print("TOP 3 WRITE-OFFS")
for n, pair in enumerate(by_value, start=1):
    if n > 3:
        break
    value, sku = pair
    print(f"{n}. {sku:<10}{value:>7.2f}")
TOP 3 WRITE-OFFS 1. SKU-112 45.00 2. SKU-118 30.00 3. SKU-102 15.50

by_value holds (value, sku) — the same information, reordered so that value is compared first. by_value.sort(reverse=True) sorts in place, largest first. Because .sort() mutates and returns None, it is called as a statement on its own line; assigning its result would throw the list away.

enumerate(by_value, start=1) supplies the ranking numbers, and if n > 3: break stops after three. The break is doing real work here — it leaves the loop entirely — which is the test §8 of Chapter 3 gives for whether a flow keyword belongs. Note also that this prints three rows only because there are at least three; with two write-offs it prints two and no error, because the loop simply runs out.

Example 3 — The pipeline, with the results kept

This one integrates everything: Chapter 2's validation and risk scoring, Chapter 3's guard clauses and accumulators, and this chapter's lists. Five orders in; each is rejected, flagged for review, or shipped. The difference from every previous version is that the outcomes are kept and can be reported in whatever order suits the reader, rather than printed as they fly past.

ALLOWED = ("GB", "IE", "FR")

orders = (
    ("ORD-7101", "a@shop.co", "GB", "1240.00",   3, None),
    ("ORD-7102", "bad.email", "GB",  "200.00", 400, "07700900123"),
    ("ORD-7103", "c@shop.co", "IE",  "640.00",  90, "07700900555"),
    ("ORD-7104", "d@shop.co", "DE",   "80.00",  12, None),
    ("ORD-7105", "e@shop.co", "FR",  "300.00",  90, None),
)

rejected = []
flagged = []
shipped = []

for order_id, email, dest, raw_value, age, phone in orders:
    if "@" not in email:
        rejected.append((order_id, "bad email"))
        continue
    if dest not in ALLOWED:
        rejected.append((order_id, f"no shipping to {dest}"))
        continue

    value = float(raw_value)
    risk = 0
    if age < 7:
        risk = risk + 30
    if value > 1000:
        risk = risk + 25
    if phone is None:
        risk = risk + 15

    if risk >= 25:
        flagged.append((risk, order_id))
    else:
        shipped.append((order_id, value))

flagged.sort(reverse=True)

print(f"{len(orders)} orders in")
print("FLAGGED FOR REVIEW")
if flagged:
    for risk, order_id in flagged:
        print(f"  {order_id}  risk {risk:>3}")
else:
    print("  none")
print("REJECTED")
if rejected:
    for order_id, reason in rejected:
        print(f"  {order_id}  {reason}")
else:
    print("  none")
if shipped:
    total = 0.0
    for order_id, value in shipped:
        total = total + value
    print(f"{len(shipped)} shipped, {total:,.2f} dispatched")
else:
    print("nothing shipped")
5 orders in FLAGGED FOR REVIEW ORD-7101 risk 70 REJECTED ORD-7102 bad email ORD-7104 no shipping to DE 2 shipped, 940.00 dispatched

Three things are worth pointing at.

The two continue statements are genuine guard clauses. Each says "this row is finished with, move on", and crucially there is code after them — the whole risk-scoring block — which is exactly the test for whether continue is earning its place. Written with nested if/else instead, the scoring logic would sit three levels deep.

The report is decoupled from the scan. The loop decides outcomes; the printing happens afterwards, from lists. That is why flagged orders can appear sorted by risk even though they were discovered in arrival order — something no amount of cleverness could have achieved while printing inside the loop.

Every summary is guarded. if flagged:, if rejected:, if shipped: — three branches that never fire on this data. A batch where nothing is rejected is the good day, and the good day should not print a heading with nothing under it.

What this chapter established

You can now keep what a scan finds. Concretely: the list literal and the empty list; append to grow, item assignment to replace, pop, insert and remove to edit, and the cost of each; the record-versus-collection distinction that decides between tuple and list; sum, max and min, built by hand first and then borrowed, along with the empty-sequence error that comes with two of them; selection sort written out in full, then sorted and .sort and the difference between them; sorting records by a chosen field by putting it in front; enumerate for position and item together; and zip, with the silent truncation that makes it dangerous.

The exercises will not let you print inside the loop and call it done. Every one of them needs something collected first and reported afterwards.
