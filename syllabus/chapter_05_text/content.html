Chapter Five

Reading What Arrives

Every value you have been given so far arrived pre-split, correctly typed, and in a tuple someone else built. Real data does not. It arrives as one long line of text with a delimiter in it, and turning that into something a program can use is the most common job in software.

Why this chapter exists

Look at how every exercise so far has started:

orders = (
    ("ORD-8101", "a@shop.co", "GB", "1240.00", 3, "GB", None),
    ("ORD-8102", "bad.email", "GB",  "200.00", 400, "GB", "07700900123"),
)

Somebody has already done the hard part. The row is split into fields, the fields are in the right order, the numbers that should be numbers are numbers and the ones that should be text are text. All you had to do was unpack it.

That file does not exist. What actually arrives from a supplier, a log, an export or an API is this:

line = "ORD-8101|a@shop.co|GB|1240.00|3|GB|"

One string. Seven fields you cannot yet reach, a delimiter you have to know about, an empty last field that means "no phone number", and a number that is currently the text "1240.00". Before any of Chapter 4's list-building can happen, somebody has to turn that line into a row — and from this chapter onward, that somebody is you.

Why this is the most common job in software Data crosses every boundary as text. A file is text. An HTTP response is text. A log line is text. A CSV export, a config file, a command-line argument, a form submission — all text. Programs hold structured values in memory, but the moment anything leaves one program and enters another it flattens into characters, and the receiving program has to rebuild the structure. Parsing is not a beginner topic you pass through; it is a large fraction of what production code actually does.

The running example is a supplier feed arriving as raw text: inconsistent spacing, mixed capitalisation, missing fields, and the occasional line that should never have been sent.

1. A string is a sequence, and you already know how to use it

Chapter 3 mentioned this in passing and Chapter 4 leaned on it without saying so. It is worth stating outright: a string is a sequence of characters, and every read operation you learned for tuples and lists works on one.

code = "ORD-8101"

print(len(code))
print(code[0])
print(code[-1])
print("ORD" in code)
print("XYZ" in code)

for ch in "GB":
    print(ch)
8 O 1 True False G B

len counts characters. code[0] indexes from zero, code[-1] counts back from the end, and for ch in ... walks one character at a time — exactly as they did for a tuple of orders. Asking for a position that does not exist raises IndexError, same as before.

in is the one that behaves differently, and Chapter 3 flagged it: on a tuple or list, in tests whether an item is a member; on a string it tests whether text appears anywhere inside as a substring. That is why "ORD" in code is True even though "ORD" is not a character.

print("O" in "ORD-8101")
print("D-8" in "ORD-8101")
print("O" in ("ORD-8101", "ORD-8102"))
print("ORD" in ("ORD-8101", "ORD-8102"))
True True False False

The last two are the trap in the round. On the tuple, in compares against whole items — and "ORD" is not equal to "ORD-8101", so it is False. Same keyword, same-looking data, opposite question. Whenever you write in, know whether the thing on the right is a string or a collection.

2. Slicing: taking a section

Indexing gives you one character. Slicing gives you a run of them, and it is written with a colon inside the brackets:

code = "ORD-8101"

print(code[0:3])
print(code[4:8])
print(code[:3])
print(code[4:])
print(code[-4:])
ORD 8101 ORD 8101 8101
Definition

A slice s[start:stop] produces a new string containing the characters from position start up to but not including stop. Omitting start means "from the beginning"; omitting stop means "to the end". Negative positions count back from the end.

The exclusive end is the same convention as range(0, 3) giving 0, 1, 2 — and it is deliberate, because it makes two useful things true. s[0:3] is exactly three characters long, so stop - start is the length. And s[:n] and s[n:] fit together perfectly with nothing lost or duplicated:

code = "ORD-8101"
print(code[:4] + code[4:])
print(code[:4] + code[4:] == code)
ORD-8101 True

Slicing never raises IndexError. Ask for more than exists and you get whatever is there, including the empty string — which is occasionally a bug that hides, so it is worth knowing:

code = "GB"
print(code[0])
print(code[0:99])
print(code[5:9])
print(len(code[5:9]))
G GB 0

code[5:9] on a two-character string is not an error. It is the empty string, printed as a blank line. Compare that with code[5], which would raise IndexError — indexing is strict, slicing is forgiving.

Slicing works on tuples and lists too, producing a new tuple or list. That is why it was deferred to this chapter rather than taught in Chapter 4 — the syntax belongs to sequences in general, and strings are where it earns its keep first.

skus = ["SKU-1", "SKU-2", "SKU-3", "SKU-4"]
print(skus[:2])
print(skus[2:])
['SKU-1', 'SKU-2'] ['SKU-3', 'SKU-4']

That gives you "the top three" for free, incidentally — Chapter 4's exercise 3 counted to three with enumerate and break because slicing had not arrived yet. sorted(x, reverse=True)[:3] does the same job in one expression, and you now understand what both are doing.

3. Strings cannot be changed

Chapter 4 divided Python's types into two camps: mutable and immutable. Lists could be changed in place; tuples refused. Strings are immutable, and they refuse in exactly the same way:

code = "ORD-8101"
code[0] = "X"
Traceback (most recent call last): File "example.py", line 2, in <module> code[0] = "X" ~~~~^^^ TypeError: 'str' object does not support item assignment

The same error, word for word, that a tuple gives. Which means every string operation that appears to change something is really producing a new string and leaving the original alone — and if you want to keep the result, you have to say so:

raw = "  gb  "
raw.strip()
print(f"[{raw}]")

cleaned = raw.strip()
print(f"[{cleaned}]")
[ gb ] [gb]

The first raw.strip() runs, produces a cleaned string, and throws it away, because nothing was assigned. raw is untouched. This is the mirror image of the append trap from Chapter 4 §2 — there, a method changed the object and returned None, so assigning the result destroyed your list. Here, a method returns a new value and changes nothing, so not assigning the result loses your work.

One rule that covers both Methods on mutable objects tend to change the object and return None — list.append, list.sort. Methods on immutable objects cannot change anything, so they return a new value — str.strip, str.replace. The tell is the return: if a method hands you something back, that something is the point. If it hands back None, the change already happened.
\n\n

4. The methods that do the everyday work

These are methods, called with a dot, exactly like list.append — but each returns a new string rather than modifying anything.

Cleaning

raw = "   GB\n"

print(f"[{raw.strip()}]")
print(f"[{raw.rstrip()}]")
print(f"[{'xxORDxx'.strip('x')}]")
[GB] [ GB] [ORD]

strip() removes whitespace from both ends — spaces, tabs, and newlines, which matters enormously when reading files, since every line arrives with a \n on the end. lstrip() and rstrip() do one end only. Given an argument, strip removes any of those characters instead of whitespace. It never touches the middle.

Case

print("gb".upper())
print("GB".lower())
print("gb" == "GB")
print("gb".upper() == "GB")
GB gb False True

Comparison is case-sensitive, so "gb" == "GB" is False. When input comes from humans or from several systems at once, **normalise before comparing** — pick one case, convert, then compare. Doing it on both sides is the safe habit: a.lower() == b.lower().

Testing

code = "ORD-8101"

print(code.startswith("ORD"))
print(code.endswith("01"))
print("8101".isdigit())
print("81a1".isdigit())
print("".isdigit())
True True True False False

startswith and endswith return True or False and are clearer than slicing for the same job — code.startswith("ORD") says what it means, where code[:3] == "ORD" makes the reader count. isdigit() is the guard you want before int(): it tells you whether the conversion will succeed instead of finding out by crashing. Note the empty string is False, which is the right answer and a common oversight.

Finding and replacing

line = "ORD-8101|a@shop.co|GB"

print(line.find("|"))
print(line.find("@"))
print(line.find("ZZZ"))
print(line.count("|"))
print("a  b   c".replace(" ", ""))
8 10 -1 2 abc

find returns the position of the first occurrence, or -1 if there is none. That -1 is a real trap: it is a valid index, so using it without checking silently reads the last character instead of failing. Always compare against -1 before using the result.

count counts non-overlapping occurrences, and replace(old, new) replaces every occurrence — both returning new values, changing nothing.

5. Build before you borrow: splitting by hand

The single most useful string operation is turning one delimited line into a list of fields. Before meeting the built-in, write one — using only Chapter 4's lists and this chapter's slicing.

line = "ORD-8101|a@shop.co|GB"

fields = []
field_start = 0

for i in range(len(line)):
    if line[i] == "|":
        fields.append(line[field_start:i])
        field_start = i + 1

fields.append(line[field_start:])

print(fields)
print(len(fields))
['ORD-8101', 'a@shop.co', 'GB'] 3

Walk it, because every part matters. field_start remembers where the current field began — it is an accumulator holding a position rather than a total. The loop looks at each character; when it finds a delimiter, everything from field_start up to but not including the delimiter is one complete field, which is exactly what the slice line[field_start:i] gives. Then field_start moves to i + 1, just past the delimiter, ready for the next field.

The line after the loop is the one people forget. The last field has no delimiter after it, so nothing inside the loop ever appends it. line[field_start:] — from the last delimiter to the end — completes the job. Delete that line and you silently lose the final field of every row, which is the classic hand-rolled parser bug.

Step through a hand-rolled split

The parser from §5, one character at a time. Watch field_start stay put while i advances, and note what happens on the very last step — the field that no delimiter ever completes.

\n

The borrowed version

line = "ORD-8101|a@shop.co|GB"

print(line.split("|"))
print("a b  c".split())
print("ORD-8101|a@shop.co|GB".split("|", 1))
['ORD-8101', 'a@shop.co', 'GB'] ['a', 'b', 'c'] ['ORD-8101', 'a@shop.co|GB']

split(sep) does what you just wrote, returning a list of strings — which is why it waited for Chapter 4. Three behaviours worth knowing:

  • With no argument, it splits on any run of whitespace and discards empties — note "a b c" giving three fields, not four. That is a different algorithm from splitting on a specific character, and it is usually what you want for human-typed text.
  • With a separator, empty fields are preserved. "a||b".split("|") gives ['a', '', 'b'] — the empty string in the middle is a real field that happened to be blank, and throwing it away would shift every column after it.
  • With a count, it stops after that many splits. Useful when the last field may legitimately contain the delimiter.

The inverse is join, and its shape surprises everyone once — the separator is the string, and the sequence is the argument:

fields = ["ORD-8101", "a@shop.co", "GB"]

print("|".join(fields))
print(", ".join(fields))
print("".join(fields))
ORD-8101|a@shop.co|GB ORD-8101, a@shop.co, GB ORD-8101a@shop.coGB

Read "|".join(fields) as "put a pipe between each of these". It is written that way because the separator is what knows how to do the joining, and because it works with any sequence of strings. Every item must already be a string — join on a list of numbers raises TypeError rather than converting for you.

Worked examples

Example 1 — A supplier feed that has been through several hands

Four lines of raw text. One has inconsistent spacing and lowercase, one is missing its price, one is out of stock. Turn what is usable into rows and report the rest.

The reasoning first. Every line gets strip() then split("|") — and the field count is checked before anything is unpacked, because a short line would otherwise raise IndexError on a field that is not there. After that each field is stripped individually, because whitespace hides between delimiters as well as at the ends. Validation happens before conversion: isdigit() before int(), an emptiness check before float(). Every failure is a guard clause with continue — the shape from Chapter 3 §8 — so the successful path stays at one indent level.

feed = (
    "SKU-301|Blue Mug|12|4.99",
    "  sku-302 | Red Mug |0| 5.49  ",
    "SKU-303|Green Mug|7|",
    "SKU-304|Yellow Mug|3|6.25",
)

stocked = []
problems = []

for line in feed:
    fields = line.strip().split("|")

    if len(fields) != 4:
        problems.append((line.strip(), f"expected 4 fields, found {len(fields)}"))
        continue

    sku = fields[0].strip().upper()
    name = fields[1].strip()
    raw_qty = fields[2].strip()
    raw_price = fields[3].strip()

    if not raw_qty.isdigit():
        problems.append((sku, "quantity is not a number"))
        continue

    if raw_price == "":
        problems.append((sku, "price is missing"))
        continue

    qty = int(raw_qty)
    price = float(raw_price)

    if qty == 0:
        problems.append((sku, "out of stock"))
        continue

    stocked.append((sku, name, qty, price))

print(f"STOCKED ({len(stocked)})")
if stocked:
    for sku, name, qty, price in stocked:
        print(f"  {sku:<10}{name:<14}{qty:>4}{price:>8.2f}")
else:
    print("  none")

print(f"PROBLEMS ({len(problems)})")
if problems:
    for what, why in problems:
        print(f"  {what:<10}{why}")
else:
    print("  none")
STOCKED (2) SKU-301 Blue Mug 12 4.99 SKU-304 Yellow Mug 3 6.25 PROBLEMS (2) SKU-302 out of stock SKU-303 price is missing

Notice what fields[0].strip().upper() does in one line: two methods chained, each taking the result of the last. " sku-302 " becomes "sku-302" becomes "SKU-302". Chaining works because every string method returns a string, so the next method has something to act on — and it reads left to right in the order the operations happen.

And note the order of the guards. isdigit() is checked before int() is ever called, so a malformed quantity produces a clear message instead of a crash. That is the same principle as Chapter 4's exercise 5 fix — convert only after you know the row is worth processing.

Example 2 — Unpacking a line into named fields

Once a line is split, Chapter 3's unpacking does the rest — and the empty trailing field turns out to carry meaning.

line = "ORD-8101|a@shop.co|GB|1240.00|3|GB|"

fields = line.split("|")
print(len(fields))
print(fields)

order_id, email, dest, raw_value, raw_age, billing, phone = fields
print(f"[{phone}]")
print(phone == "")

if phone == "":
    phone = None

print(phone is None)
7 ['ORD-8101', 'a@shop.co', 'GB', '1240.00', '3', 'GB', ''] [] True True

line.split("|") on a line ending in | produces a final empty string, and that is correct rather than a bug: the field exists and is blank. The count is 7, which matches the seven names on the left of the assignment, so unpacking works — and if the line had six fields it would raise ValueError: not enough values to unpack, which is a far better failure than silently shifting every column.

The last step converts the empty string to None, because "" and None mean different things: "" is "a phone field that is blank", None is "no phone number". Chapter 3 taught None as the sentinel for "nothing"; this is where raw text gets translated into it. Every exercise so far has been handed None already in place — now you can see who put it there.

What this chapter established

You can now take raw text and produce structured data. Concretely: a string as a sequence, with indexing, len, iteration and the substring behaviour of in; slicing, its exclusive end, and its forgiveness where indexing is strict; immutability, and the rule connecting it to what a method returns; strip, case conversion, startswith, isdigit, find and its -1, count and replace; a delimiter split written by hand, including the final field the loop cannot reach, and then split and join; method chaining; and validating before converting.

Every exercise in this chapter starts from text. Nothing arrives pre-split, and several lines are wrong in ways the sample data will not show you.
