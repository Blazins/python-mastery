Chapter Three

Doing It Once for Every Order

Chapter 2 asked you to process four orders, and the only way to do it was to write the same decision chain four times. That worked, and it also produced four real bugs — every one of them a block copied and a letter not changed. This chapter removes the possibility.

Why this chapter exists

At the end of Chapter 2 you had a working order pipeline. It passed every test. It also contained this line:

elif not a_shipping_destinations:
    print(f"{b_id}  {'REJECTED':<12}we do not ship to {b_dest}")

Order B's rejection message, guarded by order A's destination check. The program shipped goods to a country it had no carrier for, silently, and every test passed — because on that particular data, A's destination happened to be valid and B's happened to be fine anyway.

That bug is not a reasoning failure. You understood the rule perfectly; you wrote it correctly three times out of four. It is a transcription failure, and transcription failures have one necessary ingredient: something to transcribe. Write the block once and there is no a_ to leave behind, because there is no b_ to change it into.

The measurement Chapter 2's submission contained roughly eighty lines of duplicated logic and four duplicate-and-forget defects. That is one defect per twenty duplicated lines, produced by someone who understood every rule involved. Repetition is not merely inelegant — it manufactures bugs at a rate you can measure.

So this chapter does two things. First it gives you a way to hold many values under one name — the tuple. Then it gives you a way to run one block of code once for each of them — the loop. Together they turn "the same work, four times, written four times" into "the same work, four times, written once."

1. Holding more than one value: the tuple

Every name you have written so far has pointed at exactly one value. a_id is one string. a_value is one float. When you had three orders you needed three sets of names, which is precisely where the trouble started.

Definition

A tuple is a single value that contains several values in a fixed order. It is written as items separated by commas, conventionally surrounded by parentheses: (1, 2, 3). Its type is tuple, and like int or str it is an ordinary value — you can bind a name to it, print it, or pass it around.

destinations = ("GB", "IE", "FR")

print(destinations)
print(type(destinations))
print(len(destinations))
('GB', 'IE', 'FR') <class 'tuple'> 3

Three things to take from that. print shows a tuple with its parentheses and commas, which is Python telling you plainly that this is one value made of three. type() — the diagnostic from Chapter 1 §3 — reports tuple. And len() is new:

Definition

len(x) is a built-in function that returns, as an int, how many items x contains. It works on tuples and on strings (where it counts characters). It is not a method or a property — it is a plain function call, the same shape as int(x) or round(x).

print(len("ORD-1001"))
print(len(()))
8 0

() is the empty tuple — zero items, perfectly legal, and len of it is 0. Remember from Chapter 2 §3 that 0 is falsy, which means an empty tuple is falsy too, and if orders: is a natural way to ask "is there anything to process?"

Reaching an individual item: indexing

Items in a tuple have positions, and you get at one by writing the position in square brackets after the tuple.

destinations = ("GB", "IE", "FR")

print(destinations[0])
print(destinations[2])
print(destinations[-1])
GB FR FR

Positions start at zero. The first item is [0], the second [1], the third [2]. This is not an arbitrary quirk — it is near-universal across programming languages, and the reason is that an index is best understood as an offset from the start. The first item is zero items along from the beginning.

The practical consequence is that the last index of a tuple of length 3 is 2, not 3. Asking for destinations[3] raises:

destinations = ("GB", "IE", "FR")
print(destinations[3])
IndexError: tuple index out of range

Add IndexError to the small list of error names from Chapter 1 §10 that you can now read at a glance. It means: that position does not exist.

A negative index counts backwards from the end, so [-1] is the last item, [-2] the one before it. This is genuinely useful — destinations[-1] says "the last one" without you having to know or compute how many there are.

A tuple cannot be changed

Once built, a tuple's items are fixed. Assigning to a position raises an error:

destinations = ("GB", "IE", "FR")
destinations[0] = "DE"
TypeError: 'tuple' object does not support item assignment

This is called being immutable, and it is a feature rather than a limitation. A tuple is the right choice when the group of values is the thing — a coordinate pair, a row from a report, one order's fields. Nothing can quietly reach in and alter it halfway through your program.

A sibling, deliberately deferred Python's list — written ["GB", "IE"] with square brackets — is the mutable counterpart: same indexing, but items can be replaced, added and removed. Lists get their own chapter, because "this collection changes over time" brings a set of problems (growing, shrinking, and the classic mistake of modifying a collection while looping over it) that deserve proper treatment rather than a footnote. Everything you learn here about indexing and looping applies to lists unchanged.

Unpacking: the thing you have already been using

Chapter 2's exercises handed you lines like this:

a_id, a_raw_value, a_age = "ORD-4001", "1240.00", 3

That was a tuple all along, and it was handed to you before it was taught — recorded in syllabus_map.md as a gap, and this is where it closes. The right-hand side builds the tuple ("ORD-4001", "1240.00", 3); parentheses are optional when the meaning is unambiguous. The left-hand side then takes it apart again and binds each item to its own name. Building it is called packing; taking it apart is unpacking.

order = ("ORD-4001", "1240.00", 3)
order_id, raw_value, age = order

print(order_id)
print(age)
ORD-4001 3

The count must match exactly. Too few names or too many and Python refuses rather than guessing which one you meant to drop:

order = ("ORD-4001", "1240.00", 3)
order_id, raw_value = order
ValueError: too many values to unpack (expected 2, got 3)

Unpacking is why the neat swap works — the classic demonstration, and worth understanding rather than memorising:

low, high = 10, 3
low, high = high, low
print(low, high)
3 10

The entire right-hand side is evaluated first, producing the tuple (3, 10), and only then is anything assigned. No temporary variable, and no moment where one of them has been overwritten and the other has not.

Membership: in against a tuple

Chapter 2 §"Other" taught in for substring tests. Against a tuple it asks a different and more useful question: is this value one of these items?

allowed = ("GB", "IE", "FR")
dest = "IE"

print(dest in allowed)
print("DE" in allowed)
print("DE" not in allowed)
True False True

Compare that with what you wrote in Chapter 2:

a_ok = a_dest == "GB" or a_dest == "IE" or a_dest == "FR"

Both are correct. But the second states the allowed countries three times, once per order, and adding Spain means editing every one of those lines. With a tuple the policy is written once, given a name, and the test reads as the sentence it is: if dest not in allowed:. This is also why the Chapter 2 grader rejected in ("A", "B") — not because it is bad, but because it would have let you skip the ache that makes this paragraph land.

2. Build before you borrow: what a loop actually replaces

Before meeting the syntax, be precise about the work it does. Here is Chapter 2's shape, reduced to its bones — three orders, one rule:

a_value = 642.50
b_value = 120.00
c_value = 500.00

if a_value >= 500:
    print(f"{a_value} ships free")
if b_value >= 500:
    print(f"{b_value} ships free")
if c_value >= 500:
    print(f"{c_value} ships free")
642.5 ships free 500.0 ships free

Look at what varies and what does not. The rule — compare against 500, print a message — is identical three times. The only thing that changes is which value is being examined. Every character of the difference between those three blocks is the single letter at the start of one name.

So the operation you want is: take these three values; for each one in turn, bind it to a name and run this block. That sentence is the loop, and Python spells it almost exactly that way.

3. The for loop

Definition

A for loop runs a block of code once for each item of a sequence, binding that item to a name you choose before each run. The form is for name in sequence: followed by an indented block. One run of the block is called an iteration.

values = (642.50, 120.00, 500.00)

for value in values:
    if value >= 500:
        print(f"{value} ships free")
642.5 ships free 500.0 ships free

Identical output, and now the rule exists once. Take the first line apart symbol by symbol:

  • for — a keyword, like if. It begins the statement.
  • value — a name you invent, not something Python supplies. It is bound to a different item on each iteration. Name it for what one item is: value, order, country — singular, because it holds one of them.
  • in — the same keyword as the membership test, used here as part of the for syntax. It is not asking a question; it is separating the name from the sequence.
  • values — the sequence to walk through. A tuple here; strings work too, and so will lists and dictionaries later.
  • : — the colon that ends any statement introducing a block, exactly as with if in Chapter 2 §4.

Then the indented block below is the body. The same four-space indentation rule from Chapter 2 applies, and the same consequences: the body is defined by its indentation and nothing else. A line that should be inside the loop but is not indented runs once, after the loop finishes, which is one of the two or three most common beginner bugs in Python.

Notice what the diagram does not contain: any mention of counting, or of a position. A for loop in Python walks the items themselves. You do not say "from index 0 up to length minus one" — that is how loops are written in some other languages and it is where off-by-one errors come from. Python hands you each item directly.

The loop name is an ordinary name

Nothing about value is special. It is rebound before each iteration exactly as x = ... rebinds, and it survives after the loop ends, holding whatever it held last:

for country in ("GB", "IE", "FR"):
    print(country)

print("after the loop:", country)
GB IE FR after the loop: FR

Relying on that leftover value is poor practice — it reads as an accident — but knowing it happens explains a whole category of confusing behaviour. Note also that the sequence can be written inline; it does not need a name of its own if it is only used once.

Looping over a string

A string is a sequence of characters, so it works without any special handling:

flags = ""
for ch in "ORD-1001":
    if ch == "-":
        flags = flags + "|"
    else:
        flags = flags + "."
print(flags)
...|....

4. A tuple of tuples: the shape that fixes Chapter 2

One order has several fields, and you have several orders. That is a tuple of tuples — and unpacking, which you met in §1, can happen right in the loop header.

orders = (
    ("ORD-1001", "642.50", "GB"),
    ("ORD-1002", "120.00", "DE"),
    ("ORD-1003", "500.00", "IE"),
)

allowed = ("GB", "IE", "FR")

for order_id, raw_value, dest in orders:
    value = float(raw_value)
    if dest not in allowed:
        print(f"{order_id}: REJECTED - we do not ship to {dest}")
    elif value >= 500:
        print(f"{order_id}: ships free")
    else:
        print(f"{order_id}: ships at 3.95")
ORD-1001: ships free ORD-1002: REJECTED - we do not ship to DE ORD-1003: ships free

Read the loop header again: for order_id, raw_value, dest in orders:. On each iteration Python takes the next inner tuple and unpacks it into three names. Those names are ordinary — no prefixes, no letters to forget, because there is exactly one block.

Now count what changes if a fourth order arrives: one line, added to orders. Not a fourth copy of the decision chain. This is the difference between code that grows linearly with the data and code that does not grow at all.

The trailing comma after the last inner tuple is legal and conventional. It means that adding a line later touches only the new line, which keeps diffs — and code review — clean.

One-item tuples need the comma ("GB") is not a tuple — the parentheses are read as ordinary grouping, and the value is just the string "GB". The comma is what makes a tuple, so a single-item tuple is written ("GB",). This matters in practice: if dest in ("GB") silently becomes a substring test rather than a membership test, and will happily accept "G".

5. Accumulating a result across iterations

Printing inside a loop is easy. The harder and far more common job is building up a single answer from many items — a total, a count, the largest so far. The pattern is always the same three steps, and it is worth naming because you will write it hundreds of times.

The accumulator pattern

1. Before the loop, create a name holding the answer for "nothing seen yet" — 0 for a sum or a count, "" for text. 2. Inside the loop, update that name using its own current value. 3. After the loop, use it.

values = (642.50, 120.00, 500.00)

total = 0.0
free_count = 0

for value in values:
    total += value
    if value >= 500:
        free_count += 1

print(f"{len(values)} orders, {free_count} shipping free, total {total:,.2f}")
3 orders, 2 shipping free, total 1,262.50

+= is the augmented assignment from Chapter 1 §6, and this is what it was built for: total += value is total = total + value. The name on the left is both the input and the output, which is exactly what "accumulate" means.

The initial value is a real decision, not boilerplate. Starting a sum at 0.0 rather than 0 keeps the type consistent from the first iteration. Starting a count at 0 is right because zero things have been counted. And the reason step 1 must happen before the loop is that putting it inside resets the answer on every pass — which produces a total equal to the last item, a bug that looks plausible enough to survive a quick glance.

Finding a maximum

The same pattern, with a comparison instead of an addition:

orders = (
    ("ORD-1001", 642.50),
    ("ORD-1002", 120.00),
    ("ORD-1003", 500.00),
)

largest_id = None
largest_value = 0.0

for order_id, value in orders:
    if value > largest_value:
        largest_value = value
        largest_id = order_id

if largest_id is None:
    print("no orders")
else:
    print(f"largest: {largest_id} at {largest_value:,.2f}")
largest: ORD-1001 at 642.50

None as the starting id, tested with is None afterwards, is the Chapter 2 §3 convention doing real work: it distinguishes "no order was largest because there were no orders" from any actual answer. Starting largest_value at 0.0 is a decision with a hidden assumption — that no value is negative. For order values that is safe. For a temperature reading it would be a bug, and the fix is to start at None too and handle the first iteration specially.

6. Counting with range

Sometimes there is no sequence to walk — you simply want to do something a fixed number of times, or you need the position of each item as well as the item.

Definition

range(stop) produces the whole numbers from 0 up to but not including stop. range(start, stop) begins at start instead. range(start, stop, step) counts in increments of step. It is a built-in, and it is designed to be looped over.

for n in range(3):
    print(n)

print("---")

for n in range(1, 4):
    print(n)
0 1 2 --- 1 2 3

The exclusive end is the point, not a trap. Because range(3) yields 0, 1, 2, it produces exactly three numbers, and they are exactly the valid indices of a three-item tuple. range(len(orders)) therefore always covers every position, whatever the length. That property is what the design is for.

Combining it with indexing gives you position and item together:

orders = ("ORD-1001", "ORD-1002", "ORD-1003")

for i in range(len(orders)):
    print(f"{i + 1:>2}. {orders[i]}")
1. ORD-1001 2. ORD-1002 3. ORD-1003

i + 1 because line numbers shown to a human start at one while indices start at zero — the one place the mismatch is genuinely yours to manage.

Prefer the direct loop If you do not need the index, for order in orders: beats for i in range(len(orders)): every time — it is shorter, it cannot go out of range, and it says what you mean. Reach for range when you need the number itself: a countdown, a fixed repetition, or a line number. Python has a neater tool for "index and item at once" called enumerate; it is deferred to the chapter on lists, where it belongs.

7. while: repeating until something becomes true

A for loop runs once per item, and the number of iterations is known before it starts. Sometimes it is not known — you repeat until a condition changes, and how long that takes depends on what happens inside.

Definition

A while loop evaluates a condition, and runs its indented body if the condition is truthy — then evaluates the condition again, and again, until it is falsy. The form is while condition:. The condition is checked before each iteration, so a body may run zero times.

remaining = 17
pallets = 0

while remaining > 0:
    remaining -= 5
    pallets += 1

print(f"{pallets} pallets, {abs(remaining)} spaces spare")
4 pallets, 3 spaces spare

Everything the condition depends on must be able to change inside the body, or the loop never ends. That is the one failure mode while has and for does not:

remaining = 17
while remaining > 0:
    print("working")     # remaining never changes — this never stops

An infinite loop does not crash. It sits there consuming the processor until you interrupt it with Ctrl+C, which raises KeyboardInterrupt and stops the program. Getting this wrong is normal; the habit that prevents it is to write the line that moves the condition at the same time as the condition itself.

Choosing between them Use for when you have a collection to walk or a known count — which is most of the time. Use while when the stopping point depends on work done inside the loop: consuming a quantity, retrying until success, processing until a sentinel value appears. If you find yourself maintaining your own counter in a while loop purely to walk a sequence, a for loop is the tool you actually wanted.

8. Leaving early: break and continue

Two keywords change the flow inside any loop.

break abandons the loop entirely — no further iterations, execution resumes after the loop body. It is how you express "I have found what I came for":

orders = (
    ("ORD-1001", 120.00),
    ("ORD-1002", 1450.00),
    ("ORD-1003", 640.00),
)

flagged = None
for order_id, value in orders:
    if value > 1000:
        flagged = order_id
        break

print(f"first high-value order: {flagged}")
first high-value order: ORD-1002

Without the break, flagged would end up holding the last matching order rather than the first — a difference that silently disappears when only one item matches, which is exactly how it survives testing.

continue abandons only the current iteration and moves to the next. It is the tool for skipping items you do not care about, and it keeps the interesting code at one level of indentation instead of buried inside an if:

orders = (
    ("ORD-1001", "642.50"),
    ("ORD-1002", None),
    ("ORD-1003", "500.00"),
)

total = 0.0
skipped = 0

for order_id, raw_value in orders:
    if raw_value is None:
        skipped += 1
        continue
    total += float(raw_value)

print(f"total {total:,.2f} across {len(orders) - skipped} orders, {skipped} incomplete")
total 1,142.50 across 2 orders, 1 incomplete

That shape has a name worth knowing: a guard clause. Check for the case you cannot handle, deal with it, and leave — so that everything below the guard can assume the good case. It is the same move as an early return in a function, which you will meet in the functions chapter.

Which points at the other half of the rule, the half that decides whether continue belongs at all: continue only earns its place when there is code after it that you want to skip. Written like this, it does nothing whatsoever:

for order_id, raw_value in orders:
    if raw_value is None:
        skipped += 1
        continue
    else:
        total += float(raw_value)

The continue is inert. It is the last statement in its block, and the else means nothing follows it in that iteration anyway — so the loop was moving on regardless. It reads as though it prevents something, and it prevents nothing. Delete it and the program is identical.

The test is mechanical: look at what comes after the continue in the loop body. If the answer is "nothing", the keyword is decoration. If the answer is "the real work", it is a guard clause and it is doing its job. The same question applies to break — but break exits the whole loop, so it almost always changes something, which is exactly why redundant continue is the common mistake and redundant break is not.

Both keywords affect only the innermost loop containing them.

9. Loops inside loops

A loop body is ordinary code, so it may contain another loop. The inner loop runs completely for every single iteration of the outer one.

warehouses = ("LDN", "MAN")
bands = ("FREE", "STANDARD")

for warehouse in warehouses:
    for band in bands:
        print(f"{warehouse} · {band}")
LDN · FREE LDN · STANDARD MAN · FREE MAN · STANDARD

Two warehouses times two bands gives four lines, and that multiplication is the thing to keep in mind: nesting a 1,000-item loop inside another 1,000-item loop is a million iterations. Most of the time a nested loop is genuinely what the problem needs — every combination of two things — but it is also where a program stops being fast without any single line looking wrong.

Nesting over one sequence: comparing a thing with its neighbours

The example above nests two loops over two different tuples. The other shape — and the one that unlocks a whole family of real problems — nests two loops over the same sequence.

Consider a supplier feed where the same product code is sometimes listed twice, and you want to report every repeat. Notice what makes this unlike anything so far: a duplicate is not a property of a row, it is a relationship between two positions. No amount of looking at one row at a time can tell you it is a repeat. You have to hold two rows at once.

That rules out the loop you have been writing. for sku in feed: hands you a value, and a value on its own does not know where it sits. To talk about positions you must loop over positions — which is exactly what range(len(...)) gives you, and why §6 introduced it.

feed = ("SKU-301", "SKU-302", "SKU-301")

for i in range(len(feed)):
    for j in range(len(feed)):
        if feed[i] == feed[j]:
            print(f"match at {i} and {j}")
match at 0 and 0 match at 0 and 2 match at 1 and 1 match at 2 and 0 match at 2 and 2

Both loops run over every position, so i and j each take every value from 0 to 2. The mechanism works — feed[i] and feed[j] really are two rows held at the same moment — but the result is wrong twice over:

  • An item is compared with itself. When i and j are both 0 you are asking whether row 0 equals row 0. It always does. That is the 0 and 0 line.
  • Every genuine pair is reported twice — once as 0 and 2, then backwards as 2 and 0. Those are the same two rows.

Both faults have a single cause: the inner loop revisits ground the outer loop has already covered. The fix is to say so directly — for each position, compare only against the positions after it.

for i in range(len(feed)):
    for j in range(i + 1, len(feed)):
        if feed[i] == feed[j]:
            print(f"{feed[i]} repeats at positions {i} and {j}")
SKU-301 repeats at positions 0 and 2

The only change is the inner range. Instead of starting at zero it starts at i + 1 — the inner loop's bounds are computed from the outer loop's variable. This is the first time a loop in this chapter has depended on another loop, and it is the whole idea: j is now guaranteed greater than i, always. An item can never meet itself, and no pair can appear in both orders, because one order is never generated.

Read range(i + 1, len(feed)) aloud as "every position after this one" and the shape stops being arithmetic and becomes the sentence you meant.

Count the filled cells: for five positions there are ten, not twenty-five. A scan like this makes n × (n − 1) ÷ 2 comparisons — still the multiplication warned about above, still growing with the square of the input, but half of it and without the diagonal.

Pairs are not counts It is tempting to answer "which rows repeat?" by counting occurrences — a running tally per code. Resist it. The moment you increment a counter you have thrown away where the item was, and positions are what the question asked for. This also explains a behaviour that otherwise looks like it needs special handling: a code appearing three times produces three pairs, not two, because there are three ways to choose two positions out of three. Scan forward from every position and that falls out on its own. Count first, and no later work can recover it.

This shape — outer loop over every item, inner loop over everything after it — is worth recognising on sight. It is how you find duplicates, compare every pair, detect collisions, or check whether any two things in a collection conflict.

A stock reconciliation report



Combining tuples, a loop, accumulators and Chapter 1's formatting into something that looks like real output. Warehouse counts against system counts; report every discrepancy and summarise.



counts = (
    ("SKU-101", 120, 120),
    ("SKU-102", 48, 51),
    ("SKU-103", 17, 9),
    ("SKU-104", 200, 200),
)

print(f"{'SKU':<10}{'SYSTEM':>8}{'COUNTED':>9}{'DIFF':>7}")
print("-" * 34)

discrepancies = 0
net = 0

for sku, system, counted in counts:
    diff = counted - system
    if diff == 0:
        continue
    discrepancies += 1
    net += diff
    print(f"{sku:<10}{system:>8}{counted:>9}{diff:>+7}")

print("-" * 34)
if discrepancies == 0:
    print("all lines agree")
else:
    print(f"{discrepancies} of {len(counts)} lines disagree, net {net:+} units")


SKU         SYSTEM  COUNTED   DIFF
----------------------------------
SKU-102         48       51     +3
SKU-103         17        9     -8
----------------------------------
2 of 4 lines disagree, net -5 units



Three things worth noticing. The continue handles "nothing to report" before any reporting work happens, so the loop body below it deals only with the interesting case. The two accumulators are initialised before the loop and used after it — the pattern from §5, twice in one program. And :+ is a format specifier you have not seen: it forces an explicit sign, so +3 and -8 line up as a column of signed numbers, which is exactly what a discrepancy report wants.



Finding the first failure, and why break matters



A dispatch run stops at the first order it cannot fulfil. Everything after it waits.



queue = (
    ("ORD-9001", 4, 10),
    ("ORD-9002", 3, 6),
    ("ORD-9003", 9, 3),
    ("ORD-9004", 1, 3),
)

dispatched = 0
blocked_on = None

for order_id, wanted, in_stock in queue:
    if wanted > in_stock:
        blocked_on = order_id
        break
    dispatched += 1
    print(f"{order_id}: dispatched {wanted} units")

if blocked_on is None:
    print(f"whole queue cleared — {dispatched} orders")
else:
    waiting = len(queue) - dispatched
    print(f"stopped at {blocked_on} — {dispatched} dispatched, {waiting} waiting")


ORD-9001: dispatched 4 units
ORD-9002: dispatched 3 units
stopped at ORD-9003 — 2 dispatched, 2 waiting



ORD-9004 wants only 1 unit and 3 are in stock, so it could have been filled — but it is not, because break ended the loop at ORD-9003 and a dispatch run is sequential. That rule takes one keyword to express.



Swap that break for continue and the program answers a different question entirely: which orders can be filled right now, ignoring queue order. Both are reasonable systems, and they put different goods on the van. The keyword is not a detail of style — it is the business rule.



Note also blocked_on = None before the loop, tested with is None after it. That is how you distinguish "the loop finished normally" from "the loop stopped early", and it is the same sentinel technique as the maximum-finder in §5.
