Chapter Two

Deciding What to Do With an Order

Chapter 1's programs did the same thing every time they ran. Real systems do not: an order over £500 ships free, one to a restricted country is held, one from a brand-new account with a mismatched billing address is flagged for review. This chapter is about programs that look at their data and choose.

Why this chapter exists

Every program in Chapter 1 was a straight line. Read values, compute, print, stop. Run it a thousand times with the same inputs and you get the same thousand outputs, and — more importantly — it did the same work regardless of what the data actually was.

Almost nothing real behaves that way. An order-processing system asks: is this order large enough for free shipping? Is the destination one we ship to? Is the payment method one we accept from a new customer? Does the billing country match the shipping country? Each question has an answer, and each answer changes what happens next.

This chapter gives you the machinery for that: how to ask a question about data and get a definite answer, how to combine several questions into one, and how to make a program take a different path depending on the result. It is the difference between a calculator and something that can be said to make a decision.

The running problem: an order arrives with a value, a destination, an account age, and a payment method. Decide what happens to it — ship it, hold it, flag it, or reject it — and say why.

1. Asking a question: comparison operators

Chapter 1 introduced bool, the type with exactly two values, and then barely used it. This is where it earns its place. A comparison operator takes two values, asks a question about them, and produces a bool.

OperatorQuestionExampleResult
==Are these equal?500 == 500True
!=Are these different?500 != 400True
<Is the left smaller?400 < 500True
>Is the left larger?400 > 500False
<=Smaller, or equal?500 <= 500True
>=Larger, or equal?500 >= 501False

The critical thing: a comparison is an expression that produces a value, exactly like 2 + 2 produces 4. It is not a special piece of syntax that only works inside an if. You can name its result, print it, and pass it around:

order_value = 642.50
free_shipping_threshold = 500.00

qualifies = order_value >= free_shipping_threshold

print(qualifies)
print(type(qualifies))
True <class 'bool'>

Naming a comparison like this is often the single best thing you can do for readability. qualifies says what the question means; order_value >= 500.00 only says what it does.

The mistake everyone makes once = and == are different operators and confusing them is the classic beginner bug. = binds a name to a value — it is a command. == asks whether two values are equal — it is a question. Writing if order_value = 500: is a SyntaxError in Python, which is a genuine kindness: in several other languages it silently compiles and quietly assigns instead of comparing.

Comparing across types

Two behaviours here bite people who have not been told about them.

Equality across types is False, not an error. An int and a str are never equal, even when they look alike:

print(500 == "500")
print(500 == 500.0)
False True

The first is the one to remember, and it is precisely the Chapter 1 trap arriving in new clothing. If a value came from a feed, a form, or a file, it is a str, and comparing it to a number gives False forever — no error, no warning, just a condition that is never true and a branch that never runs. Convert first.

The second is worth knowing too: 500 and 500.0 are different objects of different types, but they compare equal because they represent the same number.

Ordering across types is an error. Asking whether a string is less than a number is meaningless, and Python says so rather than guessing:

print("500" < 600)
TypeError: '<' not supported between instances of 'str' and 'int'

Comparing strings

Strings compare fine with each other, but by a rule that surprises people: lexicographic order by character code, one character at a time from the left.

print("apple" < "banana")     # 'a' before 'b'
print("GB" == "gb")             # case matters
print("Zebra" < "apple")      # uppercase sorts BEFORE lowercase
True False True

That last line is not a typo. Every uppercase letter has a lower character code than every lowercase letter, so "Zebra" really does sort before "apple". In practice this means country codes, product codes and email addresses arriving from different systems must be normalised before comparison, or "GB" and "gb" will be treated as different countries. Normalising is a string-method job and arrives in the strings chapter; for now, be aware that the comparison is exact and case-sensitive.

Comparing floats

Chapter 1 established that floats are stored approximately. That has a direct consequence here:

print(0.1 + 0.2 == 0.3)
False

Not a trick — 0.1 + 0.2 is 0.30000000000000004, which is genuinely not 0.3. The rule that follows: never test two computed floats for exact equality. Ask whether they are close enough instead, by checking that the size of the difference is below some small tolerance:

total = 0.1 + 0.2
expected = 0.3
tolerance = 0.000001

print(abs(total - expected) < tolerance)
True
Definition

abs(x) is a built-in function that returns the absolute value of a number — its distance from zero, with any negative sign removed. abs(-3) is 3; abs(3) is 3. It is used here because the difference could come out negative depending on which value is larger, and you care about the size of the gap, not its direction.

Comparing < and > on floats is fine — it is only exact equality that is unsafe. And note that comparing a float against a whole number you wrote yourself (price >= 500.00) is also fine, because no accumulated arithmetic error is involved.

Chained comparisons

Python lets you write a range check the way mathematics does, and it means exactly what it looks like:

order_value = 250.00

print(100 <= order_value <= 500)
True

This is genuinely a chain, not two separate comparisons — Python evaluates order_value once and checks both bounds against it. Most languages do not support this, and the equivalent there is the longer 100 <= order_value and order_value <= 500. Use the chain: it is shorter, evaluates the middle term only once, and reads as the range check it is.

2. Combining questions: and, or, not

One comparison rarely settles a real decision. Free shipping might require an order over £500 and a domestic destination. A review flag might trigger on a new account or a mismatched billing address. Python has three boolean operators for combining conditions, and they are words rather than symbols.

OperatorResultRead as
A and BTrue only when both are true"both of these"
A or BTrue when at least one is true"either of these"
not AThe opposite of A"the reverse of this"

Written out completely — these are the truth tables, and they are worth knowing cold rather than re-deriving each time:

order_value    = 642.50
destination    = "GB"
account_age_days = 3

free_shipping = order_value >= 500 and destination == "GB"
needs_review  = account_age_days < 7 or order_value > 1000
is_domestic   = not destination != "GB"   # awkward — see below

print(free_shipping, needs_review, is_domestic)
True True True

That third line is deliberately bad. not destination != "GB" is a double negative — "it is not the case that the destination is not GB" — and a reader has to unwind it. Write destination == "GB". Reach for not when it makes a condition clearer, not when it makes one longer.

Precedence

not binds tightest, then and, then or. So this:

flagged = is_new_account and value > 1000 or is_restricted

means (is_new_account and value > 1000) or is_restricted — which may or may not be what you meant. Use parentheses whenever and and or appear in the same expression. Not because Python needs them, but because the reader does, and because the version you meant and the version you wrote produce different decisions on real orders.

The error that produces no error

Read this one twice

To check whether a country is one of several, the English sentence is "if the destination is GB or IE or FR". Translated literally:

if destination == "GB" or "IE" or "FR":

This runs, raises nothing, and is always true for every destination on earth. Python reads it as (destination == "GB") or ("IE") or ("FR") — and a non-empty string is truthy (§3), so the moment the first test fails the second operand "IE" is evaluated, found truthy, and the whole thing is true.

Every comparison needs its own left-hand side: destination == "GB" or destination == "IE". A cleaner tool for this arrives with collections; for now, spell it out.

Short-circuit evaluation

Python stops evaluating a boolean expression the moment the answer is certain.

  • In A and B, if A is false the result must be false, so B is never evaluated.
  • In A or B, if A is true the result must be true, so B is never evaluated.

This is not merely an optimisation — it is a tool. It lets you put a guard first and something unsafe second, knowing the unsafe part only runs when the guard allows it:

raw_discount = ""            # the feed left this blank

has_discount = raw_discount != "" and float(raw_discount) > 0
print(has_discount)
False

float("") raises ValueError. It does not here, because the left side is false and Python never reaches the right side. Reverse the order and the program crashes. Order matters in a boolean expression, which is not true of ordinary arithmetic and catches people out.

3. Truthiness

Python lets you use non-boolean values where a condition is expected. Every value is either truthy or falsy.

Definition

A value is falsy if Python treats it as false in a boolean context. The complete list of falsy values from the types taught so far: False, None, 0, 0.0, and the empty string "". Everything else is truthy — including "0", "False", and -1.

print(bool(0), bool(0.0), bool(""), bool(None))
print(bool(1), bool(-1), bool("0"), bool("False"))
False False False False True True True True

The second line is where the danger lives. "0" is a non-empty string, so it is truthy — even though the thing it represents is zero. A feed sending "0" for a discount will pass a naive truthiness check. This is the Chapter 1 lesson again: text that looks like a number is not a number, and here it does not even fail loudly.

Definition

bool(x) is a built-in function that converts any value to True or False using the rules above. It sits alongside int(), float() and str() from Chapter 1 as the fourth type-conversion function.

Truthiness is idiomatic for checking whether something was supplied at all:

customer_note = ""

if customer_note:
    print("Note attached.")
else:
    print("No note.")
No note.

Writing if customer_note != "": would work identically. The short form is preferred Python — but only where "empty" and "false" genuinely mean the same thing for that value. For a numeric field where 0 is a legitimate value, if quantity: is a bug waiting to happen, because a real quantity of zero is indistinguishable from a missing one. There, be explicit: if quantity != 0: or if quantity is not None:.

== versus is

Chapter 1 established that a name is a label attached to an object. That gives two different questions you might ask about two names.

  • a == b — "do these have the same value?"
  • a is b — "are these the same object?"

Almost always you want ==. The exception, and the one you will use constantly, is None:

weight_kg = None          # the supplier left it blank

print(weight_kg is None)
print(weight_kg is not None)
True False

Always test for None with is None and is not None, never with ==. The reason is concrete: only one None object exists in a running Python program, so identity is exactly the right question — and unlike ==, is cannot be redefined by a custom type to lie about the answer. This is a firm convention, and code review will flag == None.

Note also that None is not the same as 0, nor "", nor False. All four are falsy, but they mean different things: None means "no value was supplied", 0 means "the value is zero". Collapsing that distinction is how a missing weight becomes a free shipment.

4. Making the program choose: if

Everything so far produces a bool. This is what acts on one.

order_value = 642.50

if order_value >= 500:
    print("Free shipping applied.")
    print("Dispatching today.")

print("Order recorded.")
Free shipping applied. Dispatching today. Order recorded.

Four pieces of syntax, each doing real work:

  • if — the keyword.
  • order_value >= 500 — the condition, any expression producing a truthy or falsy value.
  • : — the colon, ending the header line. Forgetting it is a SyntaxError and is the single most common typo in Python.
  • The indented block beneath — the statements that run when the condition is true.

Indentation is the syntax

This is genuinely new, and it is the thing that most distinguishes Python from the languages it borrowed from. Most languages mark a block with braces and treat indentation as decoration. Python has no braces. The indentation is the block.

The rules:

  • Four spaces per level. This is near-universal convention, not a language requirement, but deviating from it marks code as foreign.
  • Never mix tabs and spaces. Python raises TabError. Configure your editor to insert spaces and forget the problem exists.
  • Every line in a block must be indented the same amount. Inconsistency is an IndentationError.
  • A block cannot be empty. If you genuinely want nothing to happen, write pass — a statement that exists solely to do nothing and satisfy the syntax.

else and elif

order_value = 120.00

if order_value >= 500:
    shipping = 0.00
elif order_value >= 100:
    shipping = 3.95
elif order_value >= 25:
    shipping = 5.95
else:
    shipping = 7.95

print(f"Shipping: £{shipping:.2f}")
Shipping: £3.95

elif is short for "else if". The chain has one property that is the whole reason to use it: the conditions are tested in order, and the first true one wins. Every branch after it is skipped, whether or not it would also have been true.

Here 120.00 satisfies both >= 100 and >= 25. Only the first runs. That mutual exclusivity is what makes a band structure work, and it means the order of your branches is part of the logic, not a stylistic choice. Reverse the two middle branches and every order between £100 and £500 is silently charged the wrong amount — with no error, and a test suite that only checks a £600 order would never notice.

Trace the chain

else is the catch-all: it takes no condition and runs when every preceding test failed. It is optional — but leaving it out means that when nothing matches, nothing happens, which is rarely what you want and is a common source of "the value just never got set" bugs.

Independent ifs are a different thing entirely

Compare these two, which look similar and behave completely differently:

# A chain: at most ONE branch runs.
if value > 1000:
    print("High value")
elif is_new_account:
    print("New account")

# Separate statements: BOTH can run.
if value > 1000:
    print("High value")
if is_new_account:
    print("New account")

Choosing between them is a real decision about your problem. Use a chain when the cases are alternatives — an order sits in exactly one shipping band. Use separate ifs when the checks are independent — an order can be both high-value and from a new account, and you want both flags raised.

Nesting, and why to avoid it

A block can contain another if. It quickly stops being readable:

if destination == "GB":
    if order_value >= 500:
        if account_age_days >= 7:
            print("Free shipping")

Three levels deep to express one decision. Since all three must hold, combine them:

if destination == "GB" and order_value >= 500 and account_age_days >= 7:
    print("Free shipping")

Better still when the condition grows, name it — the name documents the rule, and the if becomes readable at a glance:

is_domestic     = destination == "GB"
is_large_order  = order_value >= 500
is_established  = account_age_days >= 7

if is_domestic and is_large_order and is_established:
    print("Free shipping")

Nesting is sometimes genuinely necessary — when the inner question only makes sense if the outer one held. But reach for it last, not first. Deeply nested conditionals are among the most reliable sources of logic bugs in real codebases, because no reader can hold four levels of context at once.

5. Choosing a value: the conditional expression

Often a branch exists only to set one name to one of two values:

if order_value >= 500:
    shipping_label = "FREE"
else:
    shipping_label = "STANDARD"

Python has a compact form for exactly this, called a conditional expression (or, informally, a ternary):

shipping_label = "FREE" if order_value >= 500 else "STANDARD"

Read it in the order written: this value, if condition, otherwise that value. The condition sits in the middle, which is unusual — most languages put it first — but it makes the common case read like a sentence.

Because it is an expression, it produces a value and can be used anywhere a value fits, including directly inside an f-string:

print(f"Shipping: {'FREE' if order_value >= 500 else 'STANDARD'}")

Use it when the choice is short and the alternatives are simple values. Do not use it when either branch needs real work, or when nesting one inside another — "A" if x else ("B" if y else "C") is where readability dies, and an if/elif/else chain is clearer.

6. Checking whether text contains something: in

One more operator, because order validation constantly needs it.

Definition

The in operator, used with two strings, asks whether the left string appears anywhere inside the right one, and returns a bool. not in asks the opposite. The check is case-sensitive and matches any position, not just the start.

email = "mike@example.com"

print("@" in email)
print("@" not in email)
print("Example" in email)   # case-sensitive
True False False

in also works with other kinds of container — lists, dictionaries, sets — where it answers "is this a member?" rather than "is this a substring". Those arrive in their own chapters. For now, treat it as a substring test.

Deliberately deferred Two things that belong to this topic and are coming later. The match statement (Python 3.10+) handles multi-way dispatch on the shape of data, and is genuinely better than a long elif chain for some problems — it needs data structures you have not met, so it waits. if x in (a, b, c), the clean way to test membership of several options, needs tuples — that is the very next chapter's territory. Until then, spell out the comparisons.

Worked examples

Example 1

Shipping bands

The problem. Charge shipping by order value: free over £500, £3.95 from £100, £5.95 from £25, £7.95 below that. Print the band and the charge.

Thinking it through. The bands are alternatives — an order sits in exactly one — so this is an elif chain, not separate ifs. The ordering question settles itself once you notice that £600 satisfies every threshold: only a descending chain gives the right answer, because the first match wins.

# Shipping charge for one order.

order_value = 120.00

if order_value >= 500:
    band = "FREE"
    shipping = 0.00
elif order_value >= 100:
    band = "STANDARD"
    shipping = 3.95
elif order_value >= 25:
    band = "SMALL"
    shipping = 5.95
else:
    band = "MINIMUM"
    shipping = 7.95

print(f"Band:     {band}")
print(f"Shipping: £{shipping:.2f}")
print(f"Total:    £{order_value + shipping:,.2f}")
Band: STANDARD Shipping: £3.95 Total: £123.95

Why set two names in each branch rather than printing there? Because the printing is the same in every case — only the values differ. Assigning in the branch and printing once afterwards means the output format is written once. If it printed inside each branch, changing the format would mean four edits and three chances to miss one.

Why else rather than elif order_value < 25? They behave identically here, but else is provably exhaustive — it is impossible for a value to fall through and leave band unset. With a final elif, a future edit to the thresholds could open a gap, and the failure would be a NameError three lines later rather than an obvious wrong answer.

Example 2

Validating an order before it is accepted

The problem. Before an order is accepted, check it: the email must contain an @, the quantity must be a positive whole number, and the destination must be one we ship to (GB, IE, FR). Report the first problem found, or accept it.

Thinking it through. "Report the first problem" is the signal for a chain, not independent ifs — once one check fails, the rest are irrelevant. This structure is worth recognising: a sequence of guards, each rejecting for a specific reason, with acceptance as the final else.

The quantity arrives as text, so it must be converted before comparison — otherwise "3" > 0 raises TypeError. And the destination check needs each comparison spelled out in full, per the trap in §2.

# Order validation. Reports the first failure only.

email        = "mike@example.com"
raw_quantity = "3"
destination  = "IE"

quantity = int(raw_quantity)

ships_here = destination == "GB" or destination == "IE" or destination == "FR"

if "@" not in email:
    print("REJECTED: email address is not valid")
elif quantity <= 0:
    print("REJECTED: quantity must be at least 1")
elif not ships_here:
    print(f"REJECTED: we do not ship to {destination}")
else:
    print(f"ACCEPTED: {quantity} units to {destination}")
ACCEPTED: 3 units to IE

Why name ships_here instead of putting it in the elif? The condition is three comparisons long. Inline, the elif line becomes unreadable and the reason for the rejection is buried in mechanics. Named, the elif reads as not ships_here — which is exactly the English sentence.

Why is ships_here computed before the chain, even though it is only used in the third branch? A fair objection: it is computed even when the email check already failed. That is a real, if tiny, waste — and it is the right trade here, because the alternative buries a three-part condition inside a branch. Legibility beats a few nanoseconds. When the wasted work is expensive — a network call, a large computation — the calculus flips, and short-circuiting becomes the tool.

Example 3 · integrating

Routing an order for fraud review

The problem. Score an order for risk and decide its route. Add 30 points if the account is under 7 days old, 25 if the order exceeds £1,000, 20 if the billing and shipping countries differ, and 15 if there is no phone number on file. Score 50 or more holds the order; 25 to 49 flags it for manual review; below 25 ships it. Report the route, the score, and the total charged.

Thinking it through. Two structures, and recognising that they are different is the whole exercise.

The risk factors are independent — an order can trip all four — so they are separate if statements accumulating into a running total, not a chain. The routing decision is alternatives — exactly one route applies — so that is a chain. Using a chain for the first would score only the highest-priority factor and silently under-detect fraud.

The missing phone number is None, not "" — the field exists in the schema but was never filled — so it is tested with is None per §3.

# Fraud risk routing for a single order.

raw_order_value  = "1240.00"
account_age_days = 3
billing_country  = "GB"
shipping_country = "DE"
phone_number     = None

order_value = float(raw_order_value)

# Independent factors — any combination can apply, so they accumulate.
risk_score = 0

if account_age_days < 7:
    risk_score += 30
if order_value > 1000:
    risk_score += 25
if billing_country != shipping_country:
    risk_score += 20
if phone_number is None:
    risk_score += 15

# Alternatives — exactly one route applies, so this is a chain.
if risk_score >= 50:
    route = "HOLD"
elif risk_score >= 25:
    route = "REVIEW"
else:
    route = "SHIP"

shipping = 0.00 if order_value >= 500 else 7.95

print(f"Risk score: {risk_score}")
print(f"Route:      {route}")
print(f"Charged:    £{order_value + shipping:,.2f}")
Risk score: 90 Route: HOLD Charged: £1,240.00

Why risk_score = 0 before the checks? Because risk_score += 30 means "take the current value and add 30" — there must be a current value. Without the initialisation the first += raises NameError. Starting an accumulator at its identity value before adding to it is a pattern you will use constantly.

Why phone_number is None and not not phone_number? They agree here, but they mean different things. not phone_number would also be true for the empty string "" — a phone field that was submitted blank rather than never filled. Those may warrant different handling, and collapsing them throws information away. Say what you mean.

Why is the shipping charge a conditional expression rather than a fourth branch? It is a two-way choice between two simple values, assigned to one name — exactly the case the form exists for. Had there been four shipping bands, the chain from Example 1 would be right instead.

What this chapter established

  • Comparison operators produce bool values and can be named, printed and combined like any other value.
  • == asks about equality; = binds a name. Ordering across incompatible types is a TypeError; equality across them is just False.
  • Strings compare case-sensitively and lexicographically; computed floats must never be compared with ==.
  • and, or, not, their truth tables, their precedence, and short-circuit evaluation as a guarding tool.
  • x == "A" or "B" is always true and is the most dangerous line in this chapter.
  • Truthiness: False, None, 0, 0.0, "" are falsy; everything else — including "0" — is truthy.
  • is None and is not None for absence; == for everything else.
  • if/elif/else, indentation as syntax, first-match-wins, and the difference between a chain and independent ifs.
  • Conditional expressions for two-way value selection; in for substring tests.
